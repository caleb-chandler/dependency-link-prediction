## Bugs found and fixed (in `pipeline.py` / `analysis.ipynb`)

1. **`pipeline.load()` crashed on `Path` objects** (`pipeline.py`). `fpath.endswith('.pkl')` was
   called directly on a `pathlib.Path`, which has no `.endswith`. Worked before only because every
   prior fpath was a CSV loaded through a different code path or passed as `str`. `geotax_complete_24h.pkl`
   is a `Path`, so this hit immediately. Fix: `fpath = str(fpath)` at the top of `load()`.

2. **Split cache key didn't include `controlled`** (`analysis.ipynb`, "new split"/"single test" cells).
   `split_path = save_dir / f"split_{seed}_{weight}.pkl"` — this pickle stores `train_neg`/`test_neg`,
   which *do* depend on `controlled` (distance-controlled vs. random non-edge sampling), but the
   filename didn't encode it. Result: running distance-matched and unmatched at the same `weight`
   would silently reuse whichever split was built first for *both* conditions, defeating the entire
   matched-vs-unmatched comparison. Fix: filename now includes `controlled`
   (`split_{seed}_{weight}_{controlled}.pkl`). (`train_path`/the positive-edge training graph does
   *not* depend on `controlled` — verified from `prepare_data`'s code path, positive train/test edges
   are chosen before the controlled/uncontrolled branch — so it doesn't need the same fix.)

3. **`output.pkl` opened in text mode for a binary pickle write** (`analysis.ipynb`, "single test" cell).
   `with open(out_file / 'output.pkl', 'w') as f: output.to_pickle(f)` — `'w'` is text mode; pickling
   writes bytes, so this would throw `TypeError: write() argument must be str, not bytes` the first time
   it actually got exercised. Fix: `'wb'`.

4. **Agg-network node schema (`COORDS_ARR` bucket of POI lat/lons) has no single node-level `latitude`/
   `longitude`**, but two `pipeline.py` functions assumed there always was one, silently defaulting to
   `0.0` instead of erroring:
   - `dist_controlled_sampler()` — used every candidate non-edge's distance to bin it against the real
     edge-distance distribution during distance-controlled sampling. With lat/lon always 0, every
     candidate had distance 0, so the sampler could only ever fill the lowest distance bin and would
     stall (5 stall rounds) on every other bin — i.e. `controlled=True` runs on this network would
     have silently produced badly under-filled / non-distance-matched negative samples, no crash, just
     wrong results with a wall of "could not fulfill quota" warnings.
   - `edge_distances_km()` — used only in the strength task's own distance-matching of strong/weak
     edges (`strength_dist_control=True`, the default). Same failure mode: all real edges would report
     distance 0, so the strong/weak distance-matching would silently degenerate to one giant bin (no
     real distance control on the strength task at all).
   Fix: both now fall back to the network's actual `COORDS_ARR` representation when there's no
   node-level lat/lon.
     - `dist_controlled_sampler`: approximates each bucket's location as the centroid (mean lat, mean
       lon) of its `COORDS_ARR`, for binning candidate non-edges. This is an approximation (the *real*
       target distribution, `DIST_KM_MEAN`, is the exact full-pairwise mean per your `88dcf0a`
       recalculation) — good enough to steer sampling into the right bin, not used as a modeled feature.
     - `edge_distances_km`: since it's only ever called on real graph edges, it just reads the edge's
       own precomputed `DIST_KM_MEAN` (falling back to `DIST_KM` for the non-agg/poi-level network)
       instead of recomputing from node coordinates — exact, not an approximation, and cheaper.

5. **"Agg Network" → "initial setup" cell loaded the graph wrong for the new `.pkl` source**
   (`analysis.ipynb`, cell right after the `# Agg Network` header). It did
   `with open(fpath, 'rb') as f: G = pipeline.load(f)` (passing the open file handle, not `fpath`,
   into `load()`, which needs the path to branch on `.pkl` vs `.csv`) and then
   `agg_df = pd.read_csv(fpath, ...)` on a `.pkl` file. Both were leftovers from when `fpath` pointed
   at the `.csv.gz` collaborator file. Fix: `G = pipeline.load(fpath)`, and `agg_df` is unpickled
   directly when `fpath` is a `.pkl` (falls back to the old `read_csv` path for the `6h` CSV network).
   This cell is a prerequisite for the Prediction Results section only because it defines the
   `return_results()` helper used there — I did *not* touch the "Basic Analyses" /
   "Geographic Dependency Analysis" cells further down that still use the old `cat||tract` node
   convention (`u.split('||')`) and `'total_visits'`/`'DIST_KM'` attrs; those are out of scope for
   tonight's ask and are already flagged in memory as stale/pre-rebuild code.

6. **`return_results(..., _return='model', ...)` vs. the function checking for `_return == 'models'`**
   (plural) (`analysis.ipynb`, same "initial setup" cell). The "Regression Table + Error Analysis" cell
   calls `_return='model'` (singular) in all 4 of its calls; the function only special-cased `'models'`,
   so it would've silently fallen through to `else: return output` (the full 7-key Series) and then
   blown up on `dm_w_model, dm_w_cm, str_dm_w_model, str_dm_w_cm = return_results(...)` (`ValueError:
   too many values to unpack`). Fixed the function to check `'model'`, matching the actual call sites.
   Also fixed a latent bug one line below in the same branch:
   `output['link_model', 'link_cm'].tolist()` used tuple-indexing (a single 2-part key) instead of
   list-indexing; changed to `output[['link_model', 'link_cm']].tolist()`. (Dead code for tonight's
   run since we always call with `include_str=True`, but wrong either way.)

7. **`run_pipeline`'s COORDS_ARR completeness check used array truthiness directly** (`pipeline.py`,
   `run_pipeline`, right after the kwargs are unpacked): `assert all(data.get('COORDS_ARR') for _, data
   in G.nodes(data=True))`. `data.get('COORDS_ARR')` is a numpy array (shape `(n_pois, 2)`), and
   `bool()` on a multi-element array raises `ValueError: The truth value of an array with more than one
   element is ambiguous` — so this assert crashed on every single call for this network (first hit
   during the very first "single test" run, controlled=True/weight='cov', right after the split had
   already finished — ~7 minutes of MST/negative-sampling work, so worth flagging that a crash here
   doesn't lose the split, only the run built on top of it). Fix: `data.get('COORDS_ARR') is not None`.
   Driver auto-resumed by skipping the already-saved split and re-running just the single-test cell.

8. **`build_feature_matrix`'s COORDS_ARR "dist" branch blew memory on this network's scale**
   (`pipeline.py`). It computed the full POI×POI cartesian product of every edge's endpoint buckets,
   stacked *all* of them (across *all* edges in the batch) into one array, and only then grouped by
   edge to average. For combo 1 (controlled=True, weight='cov') this tried to allocate a
   `(1,034,201,360, 2)` float32 array (~7.7 GiB just for one of the two coordinate arrays) and hit
   `MemoryError` — first real run of `run_pipeline` after the COORDS_ARR-assert fix above, ~2 minutes
   into it (after node2vec embeddings had already finished training, which is now wasted work per
   restart — see note below). Fix: compute the same per-edge mean (still the exact full-pairwise-mean
   statistic, matching how `DIST_KM_MEAN` itself is defined) in a loop over edges instead of one global
   stack, so peak memory is bounded by the single largest bucket-pair's combination count rather than
   the sum over every edge in the batch. Also cache each node's coordinate array once per
   `build_feature_matrix` call (nodes repeat ~690x on average across the edge list), avoiding redundant
   `nan_to_num`/`astype` conversions. This is slower than the (broken) vectorized version but the
   vectorized version cannot run to completion on this network's size at all.
   - Note for future runs: if a `run_pipeline` call fails partway through (after node2vec but before
     the model is scored), there's currently no caching of the trained embeddings — a restart re-runs
     node2vec from scratch. Not fixing this tonight since it's ~2 minutes of work, not worth the risk
     of changing `run_pipeline`'s structure while unsupervised overnight, but flagging in case combo
     failures start piling up.

9. **`sm.Logit(...).fit()` never finished / OOM'd on this network's scale, for a reason unrelated to
   Newton vs. L-BFGS** (`pipeline.py`, both the link-model fit and the strength-model fit). First
   symptom: ran for 2 hours with zero output and hadn't converged, twice in a row, on the ~7.77M-row
   x 193-feature design matrix for combo 1. **Discussed with you directly** (you were awake by this
   point) — you confirmed trying L-BFGS as a first step, reasoning that Newton-Raphson's full
   193x193-Hessian-per-iteration is much more expensive than L-BFGS's gradient-only iterations.
   Switched both `.fit()` calls to `method='lbfgs'` — but the *very next* run still failed, this time
   with an actual `MemoryError` instead of hanging, and the traceback showed the real cause: it wasn't
   in the solver loop at all. `sm.Logit.__init__` runs a rank check by default (`check_rank=True`)
   that does a full QR decomposition of the *entire* exog matrix as a float64 copy
   (`scipy.linalg.qr` via `statsmodels.tools.matrix_rank`) — an 11.2 GiB allocation on top of
   `X_train` already resident — and this happens *before* the chosen solver ever starts iterating.
   That's what was actually behind both the earlier 2-hour stalls (presumably successful-but-thrashing
   allocations depending on memory pressure at the time) and this quick, clean `MemoryError`. Fix:
   `sm.Logit(y_train, X_train, check_rank=False)` for both fits — skips only the pre-flight
   collinearity diagnostic, not anything used in the actual fit; estimates/p-values/odds-ratios are
   unaffected. Kept `method='lbfgs'` too since it's still cheaper than Newton and there's no reason to
   revert it now that the real blocker is fixed.
